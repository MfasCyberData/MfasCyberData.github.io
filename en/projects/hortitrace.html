01 / Executive overview

The system had to become faster without changing how people worked.

HortiTrace uses a PostgreSQL warehouse for daily balance reports across about 6,425 logistics partners. The warehouse had grown to 6.3 million transaction rows, but the ETL still reloaded every row each hour.

Business constraint

Keep the current way of working.

The ERP sources, MyReport reports and user workflows had to stay unchanged.

Engineering goal

Process less data on every run.

The solution had to reduce the amount of data loaded and scanned, so the gain would remain useful as the warehouse grew.

03 / Solution architecture

I kept the existing model and added two controlled derived tables.

The business sources and reports stayed unchanged. The original transaction model was retained and made incremental. I then added two physical PostgreSQL tables: a stable copy for consistent reads and an optimized table for reporting. All three models remained available in MyReport, but only one was published to the existing reporting layer at a time.

04 / Engineering decisions

I compared several options before choosing the final design.

Loading strategyIncremental window selected

Why not full reload? Its cost grows with the total table size, even when only a small part has changed.

Why not update/insert/delete? The text primary key sorted differently in the ERP and PostgreSQL, which made deletion checks unreliable.

Choice: load by creation date over a 92-day window, which keeps the reload volume bounded.

Reporting layerIndependent physical table selected

Why not query tuning alone? It can make a scan cheaper, but it does not reduce the number of rows scanned.

Why not a materialized view? MyReport’s weekly rebuild uses CASCADE and would remove dependent objects.

Choice: use an independent physical table that survives source rebuilds and avoids scanning frozen history.

ConsistencyStaging-and-rename selected

Why not TRUNCATE then INSERT? Reports could see an empty table for several minutes.

Choice: build in staging and rename the table in one atomic step. The switch takes about ten milliseconds.

05 / Project delivery and production release

I managed the project in stages, with validation before every major transition.

I was the main developer on the optimization project while also supporting day-to-day operations. The context did not justify a formal Scrum framework, so I used a validation-driven iterative approach inspired by Plan–Do–Check–Act. A change in technical supervision also required greater autonomy, with defined review points before key decisions.

Working cycle

01 · PlanDiagnose and design

Understand system behavior, identify root causes and prepare solutions A and B.

03 · CheckValidate the data

→
04 · ActFix or release

If a check failed, correct and revalidate. If it passed, prepare the production release.

06 / Data validation

I validated the data before production.

Development and testing ran in a separate environment synchronized with a recent copy of production. The full protocol contained seven tests. The public summary below shows the main checks without exposing internal details.

Main check 01Partner balances

Compared balances across about 6,425 logistics partners.

Main check 02Partner-article balances

Compared about 37,500 partner-article combinations.

Main check 03Global control total

Confirmed that the business-filtered quantity total remained zero.

All seven tests had to pass before the Go / No-go review. The same validation queries were then rerun against production data before scheduled processing was activated.
