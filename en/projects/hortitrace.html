01 / Overview

The same issue existed at both ends of the chain: too much data was being reprocessed.

HortiTrace uses a PostgreSQL warehouse to produce balance reports. Once the warehouse reached 6.3 million transaction rows, full reloads and repeated reporting calculations became increasingly expensive.

Business constraint

Keep existing reports unchanged.

ERP sources, the MyReport layer and user workflows had to remain compatible.

Engineering objective

Do less work on every run.

Reduce the amount loaded and scanned instead of optimizing one isolated query.

03 / Diagnosis

The ETL reloaded 6.3M rows every hour although only recent records could still change.

ETL

Full reload

~30 minutes per cycle and 6.3 million transaction rows processed again.

Reporting

Expensive balance reconstruction

~6.1 million rows scanned and more than one minute for some reports.

Root cause: total warehouse growth increased cost even when very little data had actually changed.

04 / Architecture

I separated ingestion logic, stable reads and the analytics-serving layer.

The original transaction model was preserved. MyReport Data was reconfigured to load only the recent window, while derived physical tables provided stable reads and historical pre-aggregation. The MyReport reporting layer continued to operate without any report changes.

05 / Engineering decisions

The architecture followed the constraints of the existing production system.

Loading92-day incremental window

Full reload cost grew with total size. Update/insert/delete checks were unreliable because the text primary key sorted differently in the ERP and PostgreSQL.

Choice: reload by creation date within the period where data can still change.

Analytics layerIndependent physical table

A materialized view would have been fragile around weekly MyReport source rebuilds and their dependencies.

Choice: an independent physical table refreshed in a controlled way.

ConsistencyAtomic staging-and-rename

TRUNCATE + INSERT could expose an empty or partial table for several minutes.

Choice: build alongside the active table and switch with a rename operation.

As the primary developer on the optimization project, I used a validation-driven iterative approach suited to a production context and a high degree of autonomy. This was not formal Scrum: every step had to be demonstrated correct before the next one moved forward.

07 / Production release

The release was a controlled change, not just a SQL copy.

The April 3, 2026 production release followed a prepared sequence: synchronize test data, run seven controls, technical Go/No-go, deploy objects in dependency order, validate production data, confirm reports and only then enable pgAgent jobs.

Synchronize→7 tests→Go / No-go→Deploy→Validate→Check reports→Enable jobs
Guardrail: no scheduled processing was enabled before production data and reports were verified.

08 / Validation

Performance only mattered if the results stayed identical.

Control 01

Balances by partner

Compared balances for roughly 6,425 logistics partners.

Control 02

Partner × item

Compared roughly 37,500 partner-item combinations.

Release criterion: all seven tests had to pass with zero discrepancy before Go/No-go and were then rerun against production data.
