01 / Context & question

A detection system has to flag attacks without burying analysts under false alarms.

Signature-based tools recognise known attacks well, but not their variants. A machine-learning model can learn behaviour instead: packet volumes, timing, duration, TCP flags.

The project started in an IoT security course as a team of three. I led the analysis presented here and built the demo application.

Key terms in this step

Network flow
One exchange between two machines (same source, destination and protocol). In this project, each row of the file is a flow described by 72 statistics computed by CICFlowMeter: packet counts and sizes, time between packets, TCP flags, active and idle periods.
IDS
Intrusion detection system: it watches traffic and raises an alert when behaviour looks like an attack. Here, the IDS is the model that classifies each flow as “benign” or “attack”.
The project question

From a flow’s statistics alone, can we tell whether it is benign or part of an attack, and with what trade-off between missed attacks and false alarms?

Before choosing a model, I needed to check what the data really contained.

02 / Exploration & quality checks (EDA)

Exploration reveals massive duplicates, contradictory labels and one attack class that looks like normal traffic.

Exploratory data analysis (EDA) means examining the data before modelling. In this project it has two roles: catch what would distort the evaluation (duplicates, inconsistencies) and anticipate where the model will struggle.

What I checked
  1. the class distribution: benign traffic and ten attack types (FTP and SSH brute force; Hulk, GoldenEye, Slowloris, SlowHTTPTest denial of service; HOIC and LOIC-UDP DDoS; botnet; Infiltration);
  2. constant columns and impossible values (negative durations);
  3. exactly identical rows;
  4. identical flows carrying different labels;
  5. the destination ports of each class.

What these findings change

Duplicates must go before the split: otherwise the same flow would be learned and then “recognised” at test time, inflating the score. The high share of attacks (far more than in reality) rules out judging on accuracy alone. And the resemblance between Infiltration and normal traffic anticipates where the errors will concentrate.

These findings set the cleaning rules.

03 / Cleaning

Remove what would distort the evaluation, keep what carries meaning.

Cleaning decisions
  1. removed the 66,935 exact duplicates;
  2. removed the 3,036 rows whose identical values carry different labels: no model can be right on both;
  3. removed one row with a negative flow duration (measurement error);
  4. removed 8 constant columns, which carry no information;
  5. kept the −1 value of Init Bwd Win Byts, which means “TCP window not observed” and remains useful information.

04 / Training, validation and test split

Three separate sets, each with a precise role.

Training · 123,730models learn
Validation · 26,514model and threshold choice
Test · 26,514final evaluation, once

Key terms in this step

Validation set
Here, 26,514 flows the models never learn from. I use them to compare the three models, tune the gradient boosting and choose the 0.48 alert threshold.
Test set
26,514 other flows, used once at the end, like never-seen traffic.
Stratified split
Each set keeps the same share of every attack family.

A fingerprint check confirms that no flow appears in two sets at once.

With this frame, three model families could be trained under the same conditions.

05 / Three models, one rule for judging them

A linear model, a forest of trees and gradient boosting.

Linear baselineLogistic Regression

Weighs the statistics to separate benign from attack with a simple boundary. Durations range from microseconds to minutes, so I first apply a log transform, then scaling.

Tree ensembleRandom Forest

Many decision trees, learned on different draws of the data, voting together.

BoostingGradient boosting

Trees built one after another, each correcting the previous ones’ errors.

Key terms in this step

Detection rate
Share of attack flows the model flags. A missed attack is the main risk.
False-alarm rate
Share of benign traffic wrongly flagged. Too high, it wears analysts out.
Macro F1
A summary metric giving benign traffic and attacks equal weight; it can only be good if both classes are well recognised.

Transformations and models only see the 123,730 training flows; their settings are judged on validation only.

The selected gradient boosting outputs an attack probability; what remained was deciding when to raise an alert.

06 / Choosing the alert threshold

The threshold expresses the trade-off a security team has to accept.

Key terms in this step

Alert threshold
The probability from which a flow is declared an “attack”. The lower it is, the more attacks are caught, but the more normal traffic is flagged.

I chose 0.48, the threshold that maximises Macro F1 on validation. It was frozen before any evaluation on the test set.

With model and threshold fixed, the test set could be used, once.

Precision: one alert in nine is false.

Macro F1 0.877 and ROC-AUC 0.964: the area under the ROC curve means that, picking one attack flow and one benign flow at random, the model gives the attack the higher probability 96% of the time.

This overall score hides a very uneven result depending on the type of traffic.

08 / Where the errors come from

Almost every error sits on one boundary: benign traffic versus Infiltration.

This is what exploration anticipated: attacks aimed at one specific service are easy to spot, while Infiltration uses the same services as normal traffic. Researchers have also documented labelling errors in this dataset (Liu, Engelen et al., IEEE CNS 2022), so part of the remaining error probably comes from the labels rather than the model.

CheckThe model does not just read the port

Retrained without the destination port, it loses less than 0.01 Macro F1 on validation: it relies mostly on how flows behave.

CautionTiny families after cleaning

FTP-BruteForce and SlowHTTPTest have only 4 and 6 test flows: their 100% holds for a handful of examples only.

A model is only worth something if it can be used, so I built a demo application.

09 / Demo application

An application that scores every flow exactly the way the model was evaluated.

Key terms in this step

Model artifact
A single file exported by the notebook, containing the trained model, the ordered list of the 64 features and the 0.48 threshold. The application loads only this file.
Notebook/application gap
A common failure where the application prepares data differently from the notebook: the model answers without visible error, but wrongly. The single artifact and checking columns by name prevent it.
How I verified the application
  1. the artifact reloaded from disk, with shuffled columns, reproduces all 26,514 test verdicts exactly;
  2. ten automated checks: normal upload, 44-sample-flow run, reversed column order, missing column, non-numeric value, empty file, HTML escaping;
  3. real browser screenshots, on desktop and mobile.
Scope.

Local demonstration: no authentication or network exposure, debug mode off. Real authentication would be required before any deployment.

It remains to place what this work brings, and its limits.

10 / Real-world value, limits & lessons

A triage tool for analysts, not a replacement for existing tools.

In a SOC (security operations centre), this kind of model would act as a triage layer: it flags flows for review alongside signature-based detection. The threshold would be set from the team’s tolerance for false alarms on real traffic volumes.

  • Public lab traffic, not a production network.
  • Artificial attack share (60%): real-world precision would differ.
  • Questionable Infiltration labels.
  • Flow statistics exist only once a flow ends: no packet-level detection.
  • The traffic is not specific to IoT devices, despite the course’s IoT framing.
What I learned

A score is only worth something if the data is clean and the application serves exactly what was evaluated. That discipline (check, separate, validate before shipping) is the same as in analytics engineering, where a transformation that runs differently in production produces wrong numbers nobody notices.

Going further

Next steps I would take: test the model on another capture day or another dataset, recalibrate the threshold on a realistic benign/attack ratio and monitor drift once in service. The notebook details every step and its outputs.
